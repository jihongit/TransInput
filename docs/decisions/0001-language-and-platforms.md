# ADR-0001：共享核心与平台语言

日期：2026-10-21。状态：采纳，适用于新一代独立实现。

## 决策背景

用户确认 Windows 为当前版本，后续需要 macOS 和手机端；重视安全、好用、流畅、主流工具链与长期维护，不以用户当前熟悉的语言作为选型约束。允许合规使用通用 UI 框架和词库，并授权根据对比建议采用语言方案。

早期“整个产品统一使用 C++20”的建议只围绕 Windows 首版，已经被本决策取代。所有平台共用算法，不要求 UI 和系统接入也使用同一种语言。

## 已采纳

| 层 | 选择 |
| --- | --- |
| 跨平台共享核心 | Rust，稳定版工具链；初始按 edition 2024 设计，具体最低版本与依赖在构建原型中锁定 |
| Windows 系统接入 | C++20 + Windows SDK / TSF / COM 的薄适配层 |
| Windows 候选 / 设置 | 轻量原生候选绘制；设置优先 WinUI 3，原型核对部署成本与最低系统版本 |
| macOS | Swift + InputMethodKit；AppKit 候选窗、SwiftUI 设置 |
| Android | Kotlin + InputMethodService；View / Compose 的具体键盘组合由性能原型决定 |
| iOS / iPadOS | Swift + Keyboard Extension，UIKit / SwiftUI 按职责组合 |
| 跨平台 UI 框架 | 可采用，但暂不为少量设置页面引入 Qt / Flutter 等额外完整运行时；页面复杂度增长后再比较收益 |

## 为什么核心选择 Rust

- 共享算法和数据模块需要长时间维护，所有权与借用约束有助于在编译期发现多类生命周期和并发访问问题。
- 可编译为原生库，能够通过明确边界嵌入各平台输入法；不要求在客户端中加载解释器或完整桌面 UI 运行时。
- 统一的依赖、构建、格式、静态检查和测试流程便于持续维护；具体工具与版本须固定，并审查传递依赖。
- 已有真实输入法采用 Rust，包括 Windows TSF 场景。这证明存在实施路径，不证明新项目天然兼容所有宿主。

Rust 的 `unsafe`、FFI、COM 生命周期及系统线程要求仍需人工审查。死锁、输入状态错误、资源耗尽、焦点及兼容性问题仍要通过架构和测试处理。

## C++ 的地位

C++ 是可行且成熟的共享核心备选：Rime / Mozc 已有公开实践，Windows、Apple 及 Android NDK 的原生工具链成熟。本次选择 Rust 并不基于“Rust 一定更快”或“C++ 无法跨平台”的判断。

Windows 薄接入层继续使用 C++，将直接依赖 TSF / COM 的部分限制在较小范围。窗口绘制与业务算法解耦，不能因此把整个跨平台核心重新写成 Windows 代码。

## 已比较的其他方向

| 方向 | 取舍 |
| --- | --- |
| 全部使用 C++ / Qt | 核心及桌面 UI 的工具链集中，但手机输入法接入仍需平台代码；Qt 模块、平台版本与分发许可另需核对 |
| 全部使用 Rust，包括所有 UI | 核心安全约束统一，但原生 UI 生态和平台桥接成本必须逐端承担，不能以一种语言为目标忽略维护成本 |
| Flutter / Dart 统一所有界面 | 设置应用可共享较多代码；候选窗、键盘扩展、焦点与生命周期仍需原生接入，并增加运行时预算 |
| 仅 Swift | Apple 平台很合适；不作为 Windows / Android 全产品共享技术栈的基线 |
| 仅 Kotlin / Kotlin Multiplatform | 适合 Android，并有共享逻辑路线；本项目低层 Windows 接入和原生库边界仍需专门验证，不作为首选 |
| C# / .NET | 可用于 Windows 设置与 COM 互操作；当前选择减少主要层的额外语言数量，不把 .NET 当作全平台输入核心基线 |

## 验证与调整条件

P1 先验证原生库装载 / 卸载、C ABI / IPC 所有权、TSF 文本编辑、焦点切换和候选渲染，不先写完整引擎。Windows 主线阶段就保留 Apple / Android 编译探针，尽早暴露平台耦合。

若在指定系统版本、架构、扩展预算或可维护性上出现有证据的阻碍，记录复现、比较代价后新增 ADR 调整相应层。优先调整局部桥接和承载方式，不能凭偏好在多种语言间反复重写整个核心。
